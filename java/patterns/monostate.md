# Monostate

> **Autogenerated from:** `references/java-design-patterns/monostate`

## When to Use
- When you need to decouple monostate implementation from client code
- When the monostate logic varies independently from the rest of the system
- When you want to enforce a consistent monostate interface across implementations
- When the monostate behavior needs to be configured or swapped at runtime
- When standardizing monostate handling across a team or codebase

## Common Mistakes

```java
// WRONG: Treating Monostate as a true Singleton
// Multiple instances appear to work independently but share state.
// This leads to confusing bugs where one instance's changes affect another.
// Monostate behaves like a singleton but LOOKS like a regular class.
MonostateConfig config1 = new MonostateConfig();
MonostateConfig config2 = new MonostateConfig();
config1.setUrl("https://dev.example.com");

// config2.getUrl() also returns "https://dev.example.com" — surprising!

// CORRECT: Use a proper Singleton or DI when you need one instance
// Be explicit about your intent — Singleton pattern or injection scope.
@Singleton
public class AppConfig {
    private final String url;
    public AppConfig(@Value("${app.url}") String url) {
        this.url = url;
    }
}
```

```java
// WRONG: Monostate with shared mutable state, no synchronization
// Thread A writes, Thread B reads — sees stale data.
public class SharedCounter {
    private static int count = 0;  // mutable, shared, unsynchronized
    private static boolean initialized = false;

    public SharedCounter() {
        if (!initialized) {
            count = 0;
            initialized = true;  // race condition
        }
    }

    public void increment() { count++; }  // not atomic!
}

// CORRECT: Use AtomicInteger or synchronized access
public class SharedCounter {
    private static final AtomicInteger count = new AtomicInteger(0);
    private static volatile boolean initialized = false;

    public SharedCounter() {
        if (!initialized) {
            synchronized (SharedCounter.class) {
                if (!initialized) {
                    count.set(0);
                    initialized = true;
                }
            }
        }
    }

    public void increment() { count.incrementAndGet(); }
}
```

## Gotchas
- Subclassing Monostate is risky — subclasses all share the same static state.
- Testing is harder: shared static state persists across tests. Reset state in `@BeforeEach`.
- Serialization can break the illusion — deserialized instances get fresh static state.
- Monostate is less transparent than Singleton. Document the shared-state behavior clearly.
