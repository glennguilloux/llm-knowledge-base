# Command Query Responsibility Segregation

> **Autogenerated from:** `references/java-design-patterns/command-query-responsibility-segregation`

## When to Use
- When you need to decouple command query responsibility segregation implementation from client code
- When the command query responsibility segregation logic varies independently from the rest of the system
- When you want to enforce a consistent command query responsibility segregation interface across implementations
- When the command query responsibility segregation behavior needs to be configured or swapped at runtime
- When standardizing command query responsibility segregation handling across a team or codebase

## Common Mistakes

```java
// WRONG: Shared query model between reads and writes
// Leads to conflicting optimizations — read needs denormalized data,
// write needs normalized.
public class OrderService {
    public OrderDTO createAndReturn(OrderRequest req) {
        // creates order AND formats response in one method
        return formatOrderResponse(saveOrder(req));
    }
}

// CORRECT: Separate command and query models
// Commands return minimal acknowledgment; queries use a separate model.
public class OrderCommandService {
    public OrderId createOrder(OrderRequest req) {
        Order order = new Order(req);
        orderRepository.save(order);
        return order.getId();
    }
}

public class OrderQueryService {
    public OrderDTO getOrderDetails(OrderId id) {
        OrderView view = readModelRepository.findById(id);
        return OrderDTO.from(view);
    }
}
```

```java
// WRONG: Commands with heavy dependencies
// Every command handler pulls in 5+ services for validation, persistence, events
public class PlaceOrderHandler {
    @Inject InventoryService inventory;
    @Inject PaymentService payment;
    @Inject ShippingService shipping;
    @Inject EmailService email;
    @Inject AuditService audit;
    // 5 dependencies — test setup is painful
}

// CORRECT: Commands carry just enough data
// Handler delegates to a saga or orchestrator for multi-step flows
public record PlaceOrderCommand(
    CustomerId customerId,
    List<OrderLine> lines,
    PaymentMethod payment
) implements Command {}

public class PlaceOrderHandler {
    @Inject OrderSaga saga;
    public void handle(PlaceOrderCommand cmd) {
        saga.execute(cmd); // saga manages the multi-step flow
    }
}
```

## Gotchas
- Eventual consistency: query model lags behind command model. Decide on staleness tolerance upfront.
- Event replay: when rebuilding the read model from events, ensure idempotent processing.
- Duplicate event handling can corrupt read models — use idempotency keys or upsert semantics.
- CQRS adds complexity. Don't use it unless you genuinely need different read/write models.
