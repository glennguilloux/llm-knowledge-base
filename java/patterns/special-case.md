# Special Case

> **Autogenerated from:** `references/java-design-patterns/special-case`

## When to Use
- When you need to decouple special case implementation from client code
- When the special case logic varies independently from the rest of the system
- When you want to enforce a consistent special case interface across implementations
- When the special case behavior needs to be configured or swapped at runtime
- When standardizing special case handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The special case pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep special case logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle special case errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the special case abstraction
```


## Gotchas
- Over-applying special case when a simpler solution (direct call, if/else) suffices
- Thread safety: special case implementations often assume single-threaded access
- Testing complexity: mock/stub setup for special case abstractions can be verbose
