# Object Pool

> **Autogenerated from:** `references/java-design-patterns/object-pool`

## When to Use
- When you need to decouple object pool implementation from client code
- When the object pool logic varies independently from the rest of the system
- When you want to enforce a consistent object pool interface across implementations
- When the object pool behavior needs to be configured or swapped at runtime
- When standardizing object pool handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The object pool pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep object pool logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle object pool errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the object pool abstraction
```


## Gotchas
- Over-applying object pool when a simpler solution (direct call, if/else) suffices
- Thread safety: object pool implementations often assume single-threaded access
- Testing complexity: mock/stub setup for object pool abstractions can be verbose
