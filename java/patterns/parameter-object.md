# Parameter Object

> **Autogenerated from:** `references/java-design-patterns/parameter-object`

## When to Use
- When you need to decouple parameter object implementation from client code
- When the parameter object logic varies independently from the rest of the system
- When you want to enforce a consistent parameter object interface across implementations
- When the parameter object behavior needs to be configured or swapped at runtime
- When standardizing parameter object handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The parameter object pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep parameter object logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle parameter object errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the parameter object abstraction
```


## Gotchas
- Over-applying parameter object when a simpler solution (direct call, if/else) suffices
- Thread safety: parameter object implementations often assume single-threaded access
- Testing complexity: mock/stub setup for parameter object abstractions can be verbose
