# Registry

> **Autogenerated from:** `references/java-design-patterns/registry`

## When to Use
- When you need to decouple registry implementation from client code
- When the registry logic varies independently from the rest of the system
- When you want to enforce a consistent registry interface across implementations
- When the registry behavior needs to be configured or swapped at runtime
- When standardizing registry handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The registry pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep registry logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle registry errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the registry abstraction
```


## Gotchas
- Over-applying registry when a simpler solution (direct call, if/else) suffices
- Thread safety: registry implementations often assume single-threaded access
- Testing complexity: mock/stub setup for registry abstractions can be verbose
