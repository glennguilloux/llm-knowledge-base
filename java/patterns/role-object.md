# Role Object

> **Autogenerated from:** `references/java-design-patterns/role-object`

## When to Use
- When you need to decouple role object implementation from client code
- When the role object logic varies independently from the rest of the system
- When you want to enforce a consistent role object interface across implementations
- When the role object behavior needs to be configured or swapped at runtime
- When standardizing role object handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The role object pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep role object logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle role object errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the role object abstraction
```


## Gotchas
- Over-applying role object when a simpler solution (direct call, if/else) suffices
- Thread safety: role object implementations often assume single-threaded access
- Testing complexity: mock/stub setup for role object abstractions can be verbose
