# Event Driven Architecture

> **Autogenerated from:** `references/java-design-patterns/event-driven-architecture`

## When to Use
- When you need to decouple event driven architecture implementation from client code
- When the event driven architecture logic varies independently from the rest of the system
- When you want to enforce a consistent event driven architecture interface across implementations
- When the event driven architecture behavior needs to be configured or swapped at runtime
- When standardizing event driven architecture handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The event driven architecture pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep event driven architecture logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle event driven architecture errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the event driven architecture abstraction
```


## Gotchas
- Over-applying event driven architecture when a simpler solution (direct call, if/else) suffices
- Thread safety: event driven architecture implementations often assume single-threaded access
- Testing complexity: mock/stub setup for event driven architecture abstractions can be verbose
