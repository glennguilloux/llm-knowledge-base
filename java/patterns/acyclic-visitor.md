# Acyclic Visitor

> **Autogenerated from:** `references/java-design-patterns/acyclic-visitor`

## When to Use
- When you need to decouple acyclic visitor implementation from client code
- When the acyclic visitor logic varies independently from the rest of the system
- When you want to enforce a consistent acyclic visitor interface across implementations
- When the acyclic visitor behavior needs to be configured or swapped at runtime
- When standardizing acyclic visitor handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The acyclic visitor pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep acyclic visitor logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle acyclic visitor errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the acyclic visitor abstraction
```


## Gotchas
- Over-applying acyclic visitor when a simpler solution (direct call, if/else) suffices
- Thread safety: acyclic visitor implementations often assume single-threaded access
- Testing complexity: mock/stub setup for acyclic visitor abstractions can be verbose
