# Collecting Parameter

> **Autogenerated from:** `references/java-design-patterns/collecting-parameter`

## When to Use
- When you need to decouple collecting parameter implementation from client code
- When the collecting parameter logic varies independently from the rest of the system
- When you want to enforce a consistent collecting parameter interface across implementations
- When the collecting parameter behavior needs to be configured or swapped at runtime
- When standardizing collecting parameter handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The collecting parameter pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep collecting parameter logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle collecting parameter errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the collecting parameter abstraction
```


## Gotchas
- Over-applying collecting parameter when a simpler solution (direct call, if/else) suffices
- Thread safety: collecting parameter implementations often assume single-threaded access
- Testing complexity: mock/stub setup for collecting parameter abstractions can be verbose
