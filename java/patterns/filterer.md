# Filterer

> **Autogenerated from:** `references/java-design-patterns/filterer`

## When to Use
- When you need to decouple filterer implementation from client code
- When the filterer logic varies independently from the rest of the system
- When you want to enforce a consistent filterer interface across implementations
- When the filterer behavior needs to be configured or swapped at runtime
- When standardizing filterer handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The filterer pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep filterer logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle filterer errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the filterer abstraction
```


## Gotchas
- Over-applying filterer when a simpler solution (direct call, if/else) suffices
- Thread safety: filterer implementations often assume single-threaded access
- Testing complexity: mock/stub setup for filterer abstractions can be verbose
