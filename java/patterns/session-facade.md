# Session Facade

> **Autogenerated from:** `references/java-design-patterns/session-facade`

## When to Use
- When you need to decouple session facade implementation from client code
- When the session facade logic varies independently from the rest of the system
- When you want to enforce a consistent session facade interface across implementations
- When the session facade behavior needs to be configured or swapped at runtime
- When standardizing session facade handling across a team or codebase

## Common Mistakes

```java
// WRONG: Facade that exposes every subsystem method
// Just delegates each call 1:1 — provides no simplification.
// Client still needs to know the full subsystem API.
public class OrderFacade {
    private final InventoryService inventory;
    private final PaymentService payment;
    private final ShippingService shipping;

    public boolean checkStock(String sku) { return inventory.isAvailable(sku); }
    public boolean validateCard(String num) { return payment.validate(num); }
    public void schedulePickup(String addr) { shipping.schedule(addr); }
    // Client still orchestrates the flow themselves
}

// CORRECT: Facade with meaningful high-level operations
// Provides 3-4 operations that cover 80% of use cases.
public class OrderFacade {
    private final InventoryService inventory;
    private final PaymentService payment;
    private final ShippingService shipping;

    public OrderResult placeOrder(Cart cart, PaymentInfo paymentInfo) {
        if (!inventory.reserve(cart.items())) {
            return OrderResult.failed("Out of stock");
        }
        PaymentResult result = payment.charge(cart.total(), paymentInfo);
        if (!result.isSuccess()) {
            inventory.release(cart.items());
            return OrderResult.failed("Payment declined");
        }
        shipping.schedule(cart.address());
        return OrderResult.success(“Order confirmed”);
    }

    public OrderStatus getOrderStatus(String orderId) { /* ... */ }
    public CancelResult cancelOrder(String orderId) { /* ... */ }
}
```

```java
// WRONG: Facade becomes a god object
// Every subsystem feature gets a method on the facade.
// 50+ methods = no abstraction at all.
public class GodFacade {
    public void createUser() { /* ... */ }
    public void deleteUser() { /* ... */ }
    public void sendEmail() { /* ... */ }
    public void generateReport() { /* ... */ }
    public void auditLog() { /* ... */ }
    public void backupDatabase() { /* ... */ }
    // 40 more methods...
}

// CORRECT: Multiple focused facades
// Split into cohesive facades by domain concern.
public class UserFacade { /* user operations only */ }
public class ReportingFacade { /* reports only */ }
public class AdminFacade { /* admin operations only */ }
```

## Gotchas
- Facade doesn't prevent direct subsystem access — document which path clients should use.
- Session Facade in J2EE often manages transactions — ensure transaction boundaries are correct.
- Don't put business logic in the facade. It's a coordination layer, not a business layer.
- Test the facade at the integration level — unit tests against individual subsystems won't catch coordination bugs.
