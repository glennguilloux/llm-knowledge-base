# Update Method

> **Autogenerated from:** `references/java-design-patterns/update-method`

## When to Use
- When you need to decouple update method implementation from client code
- When the update method logic varies independently from the rest of the system
- When you want to enforce a consistent update method interface across implementations
- When the update method behavior needs to be configured or swapped at runtime
- When standardizing update method handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The update method pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep update method logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle update method errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the update method abstraction
```


## Gotchas
- Over-applying update method when a simpler solution (direct call, if/else) suffices
- Thread safety: update method implementations often assume single-threaded access
- Testing complexity: mock/stub setup for update method abstractions can be verbose
