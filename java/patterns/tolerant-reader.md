# Tolerant Reader

> **Autogenerated from:** `references/java-design-patterns/tolerant-reader`

## When to Use
- When you need to decouple tolerant reader implementation from client code
- When the tolerant reader logic varies independently from the rest of the system
- When you want to enforce a consistent tolerant reader interface across implementations
- When the tolerant reader behavior needs to be configured or swapped at runtime
- When standardizing tolerant reader handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The tolerant reader pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep tolerant reader logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle tolerant reader errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the tolerant reader abstraction
```


## Gotchas
- Over-applying tolerant reader when a simpler solution (direct call, if/else) suffices
- Thread safety: tolerant reader implementations often assume single-threaded access
- Testing complexity: mock/stub setup for tolerant reader abstractions can be verbose
