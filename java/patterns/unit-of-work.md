# Unit Of Work

> **Autogenerated from:** `references/java-design-patterns/unit-of-work`

## When to Use
- When you need to decouple unit of work implementation from client code
- When the unit of work logic varies independently from the rest of the system
- When you want to enforce a consistent unit of work interface across implementations
- When the unit of work behavior needs to be configured or swapped at runtime
- When standardizing unit of work handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The unit of work pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep unit of work logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle unit of work errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the unit of work abstraction
```


## Gotchas
- Over-applying unit of work when a simpler solution (direct call, if/else) suffices
- Thread safety: unit of work implementations often assume single-threaded access
- Testing complexity: mock/stub setup for unit of work abstractions can be verbose
