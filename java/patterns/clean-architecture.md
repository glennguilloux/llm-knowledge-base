# Clean Architecture

> **Autogenerated from:** `references/java-design-patterns/clean-architecture`

## When to Use
- When you need to decouple clean architecture implementation from client code
- When the clean architecture logic varies independently from the rest of the system
- When you want to enforce a consistent clean architecture interface across implementations
- When the clean architecture behavior needs to be configured or swapped at runtime
- When standardizing clean architecture handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The clean architecture pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep clean architecture logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle clean architecture errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the clean architecture abstraction
```


## Gotchas
- Over-applying clean architecture when a simpler solution (direct call, if/else) suffices
- Thread safety: clean architecture implementations often assume single-threaded access
- Testing complexity: mock/stub setup for clean architecture abstractions can be verbose
