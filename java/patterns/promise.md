# Promise

> **Autogenerated from:** `references/java-design-patterns/promise`

## When to Use
- When you need to decouple promise implementation from client code
- When the promise logic varies independently from the rest of the system
- When you want to enforce a consistent promise interface across implementations
- When the promise behavior needs to be configured or swapped at runtime
- When standardizing promise handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The promise pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep promise logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle promise errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the promise abstraction
```


## Gotchas
- Over-applying promise when a simpler solution (direct call, if/else) suffices
- Thread safety: promise implementations often assume single-threaded access
- Testing complexity: mock/stub setup for promise abstractions can be verbose
