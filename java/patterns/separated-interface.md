# Separated Interface

> **Autogenerated from:** `references/java-design-patterns/separated-interface`

## When to Use
- When you need to decouple separated interface implementation from client code
- When the separated interface logic varies independently from the rest of the system
- When you want to enforce a consistent separated interface interface across implementations
- When the separated interface behavior needs to be configured or swapped at runtime
- When standardizing separated interface handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The separated interface pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep separated interface logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle separated interface errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the separated interface abstraction
```


## Gotchas
- Over-applying separated interface when a simpler solution (direct call, if/else) suffices
- Thread safety: separated interface implementations often assume single-threaded access
- Testing complexity: mock/stub setup for separated interface abstractions can be verbose
