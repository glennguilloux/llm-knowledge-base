# Active Object

> **Autogenerated from:** `references/java-design-patterns/active-object`

## When to Use
- When you need to decouple active object implementation from client code
- When the active object logic varies independently from the rest of the system
- When you want to enforce a consistent active object interface across implementations
- When the active object behavior needs to be configured or swapped at runtime
- When standardizing active object handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The active object pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep active object logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle active object errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the active object abstraction
```


## Gotchas
- Over-applying active object when a simpler solution (direct call, if/else) suffices
- Thread safety: active object implementations often assume single-threaded access
- Testing complexity: mock/stub setup for active object abstractions can be verbose
