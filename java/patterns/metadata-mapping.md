# Metadata Mapping

> **Autogenerated from:** `references/java-design-patterns/metadata-mapping`

## When to Use
- When you need to decouple metadata mapping implementation from client code
- When the metadata mapping logic varies independently from the rest of the system
- When you want to enforce a consistent metadata mapping interface across implementations
- When the metadata mapping behavior needs to be configured or swapped at runtime
- When standardizing metadata mapping handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The metadata mapping pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep metadata mapping logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle metadata mapping errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the metadata mapping abstraction
```


## Gotchas
- Over-applying metadata mapping when a simpler solution (direct call, if/else) suffices
- Thread safety: metadata mapping implementations often assume single-threaded access
- Testing complexity: mock/stub setup for metadata mapping abstractions can be verbose
