# Master Worker

> **Autogenerated from:** `references/java-design-patterns/master-worker`

## When to Use
- When you need to decouple master worker implementation from client code
- When the master worker logic varies independently from the rest of the system
- When you want to enforce a consistent master worker interface across implementations
- When the master worker behavior needs to be configured or swapped at runtime
- When standardizing master worker handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The master worker pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep master worker logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle master worker errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the master worker abstraction
```


## Gotchas
- Over-applying master worker when a simpler solution (direct call, if/else) suffices
- Thread safety: master worker implementations often assume single-threaded access
- Testing complexity: mock/stub setup for master worker abstractions can be verbose
