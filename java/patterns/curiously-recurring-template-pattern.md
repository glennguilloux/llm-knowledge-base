## When to Use

- When the curiously recurring template pattern logic varies independently from the rest of the system
- When you want to enforce a consistent curiously recurring template pattern interface across implementations

## Common Mistakes

```java
// WRONG: Using CRTP to force compile-time type safety when runtime polymorphism suffices
// Adds unnecessary complexity — simpler interfaces work fine.
public abstract class Entity<T extends Entity<T>> {
    public abstract T copy();
}

public class User extends Entity<User> {
    public User copy() { return new User(this); }
}

// CORRECT: Use interfaces when you don't need self-referential types
// Simpler, easier to read, and avoids CRTP boilerplate.
public interface Copyable<T> {
    T copy();
}

public class User implements Copyable<User> {
    public User copy() { return new User(this); }
}
```

```java
// WRONG: CRTP with generic type erasure issues
// Type information is erased at runtime — leads to ClassCastException.
public abstract class Builder<T extends Builder<T>> {
    public abstract T self();
    @SuppressWarnings("unchecked")
    public T build() {
        doBuild();
        return (T) this;  // Unchecked cast, could fail at runtime
    }
}

// CORRECT: Accept the unchecked cast but isolate it
// Keep the cast in one well-tested location.
public abstract class Builder<T extends Builder<T>> {
    protected abstract T self();
    protected abstract void doBuild();

    @SuppressWarnings("unchecked")
    public T build() {
        doBuild();
        return self();  // self() is implemented by subclass
    }
}
```

```java
// WRONG: CRTP base class depends on concrete subclass details.
// The base class becomes hard to reuse and easy to break.
public abstract class Base<T extends Base<T>> {
    public void save() {
        ((User) this).persist();
    }
}

// CORRECT: Keep the base generic and require only the self type.
public abstract class Base<T extends Base<T>> {
    public abstract T self();
    public void save() {
        Repository.save(self());
    }
}
```

## Gotchas
- CRTP doesn't prevent subclass misuse — nothing stops `class Foo extends Bar<Baz>`.
- Java's type erasure makes runtime inspection of the type parameter impossible.
- CRTP couples the base class to its subclasses — refactoring becomes harder.
- In most cases, composition (Strategy, Visitor) is cleaner than CRTP.
