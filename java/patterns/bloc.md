# Bloc

> **Autogenerated from:** `references/java-design-patterns/bloc`

## When to Use
- When you need to decouple bloc implementation from client code
- When the bloc logic varies independently from the rest of the system
- When you want to enforce a consistent bloc interface across implementations
- When the bloc behavior needs to be configured or swapped at runtime
- When standardizing bloc handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The bloc pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep bloc logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle bloc errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the bloc abstraction
```


## Gotchas
- Over-applying bloc when a simpler solution (direct call, if/else) suffices
- Thread safety: bloc implementations often assume single-threaded access
- Testing complexity: mock/stub setup for bloc abstractions can be verbose
