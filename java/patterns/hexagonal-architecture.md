# Hexagonal Architecture

> **Autogenerated from:** `references/java-design-patterns/hexagonal-architecture`

## When to Use
- When you need to decouple hexagonal architecture implementation from client code
- When the hexagonal architecture logic varies independently from the rest of the system
- When you want to enforce a consistent hexagonal architecture interface across implementations
- When the hexagonal architecture behavior needs to be configured or swapped at runtime
- When standardizing hexagonal architecture handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The hexagonal architecture pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep hexagonal architecture logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle hexagonal architecture errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the hexagonal architecture abstraction
```


## Gotchas
- Over-applying hexagonal architecture when a simpler solution (direct call, if/else) suffices
- Thread safety: hexagonal architecture implementations often assume single-threaded access
- Testing complexity: mock/stub setup for hexagonal architecture abstractions can be verbose
