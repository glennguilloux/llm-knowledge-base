# Service Locator

> **Autogenerated from:** `references/java-design-patterns/service-locator`

## When to Use
- When you need to decouple service locator implementation from client code
- When the service locator logic varies independently from the rest of the system
- When you want to enforce a consistent service locator interface across implementations
- When the service locator behavior needs to be configured or swapped at runtime
- When standardizing service locator handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The service locator pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep service locator logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle service locator errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the service locator abstraction
```


## Gotchas
- Over-applying service locator when a simpler solution (direct call, if/else) suffices
- Thread safety: service locator implementations often assume single-threaded access
- Testing complexity: mock/stub setup for service locator abstractions can be verbose
