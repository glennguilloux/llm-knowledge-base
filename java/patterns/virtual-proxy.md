# Virtual Proxy

> **Autogenerated from:** `references/java-design-patterns/virtual-proxy`

## When to Use
- When you need to decouple virtual proxy implementation from client code
- When the virtual proxy logic varies independently from the rest of the system
- When you want to enforce a consistent virtual proxy interface across implementations
- When the virtual proxy behavior needs to be configured or swapped at runtime
- When standardizing virtual proxy handling across a team or codebase

## Common Mistakes

```java
// WRONG: Virtual proxy not thread-safe
// Multiple threads triggering lazy init simultaneously
// creates multiple instances.
public class LazyImageProxy implements Image {
    private RealImage realImage = null;  // not volatile

    @Override
    public void display() {
        if (realImage == null) {          // race condition!
            realImage = new RealImage();  // multiple threads enter here
        }
        realImage.display();
    }
}

// CORRECT: Double-checked locking or initialization-on-demand holder
@Component
public class LazyImageProxy implements Image {
    private volatile RealImage realImage;

    @Override
    public void display() {
        if (realImage == null) {
            synchronized (this) {
                if (realImage == null) {
                    realImage = new RealImage();
                }
            }
        }
        realImage.display();
    }
}
```

```java
// WRONG: Proxy doing too much — adding business logic
// The proxy is meant to defer creation, but now it also logs, audits,
// caches, and validates. Violates Single Responsibility.
public class BusyProxy implements ExpensiveObject {
    private ExpensiveObject real;
    private int accessCount = 0;

    @Override
    public void process() {
        accessCount++;
        System.out.println("Access #" + accessCount);
        if (real == null) {
            logger.info("Starting heavy initialization...");
            real = new RealObject();
            logger.info("Initialization complete.");
        }
        audit.log("process() called");
        cache.check();
        real.process();
    }
}

// CORRECT: Proxy has one job — lazy initialization
// Cross-cutting concerns use decorators or AOP.
public class VirtualProxy implements ExpensiveObject {
    private volatile ExpensiveObject real;

    @Override
    public void process() {
        if (real == null) {
            synchronized (this) {
                if (real == null) {
                    real = new RealObject();
                }
            }
        }
        real.process();
    }
}
```

## Gotchas
- Virtual proxy and protection proxy have different concerns — don't mix lazy loading with access control in the same proxy.
- If the real object is cheap to create, a virtual proxy adds unnecessary indirection.
- The proxy must implement the same interface as the real subject — interface changes require proxy updates.
- Consider `java.lang.ref.Reference` (SoftReference) for memory-sensitive lazy loading instead of a custom proxy.
