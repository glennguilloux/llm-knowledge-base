# Delegation

> **Autogenerated from:** `references/java-design-patterns/delegation`

## When to Use
- When you need to decouple delegation implementation from client code
- When the delegation logic varies independently from the rest of the system
- When you want to enforce a consistent delegation interface across implementations
- When the delegation behavior needs to be configured or swapped at runtime
- When standardizing delegation handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The delegation pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep delegation logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle delegation errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the delegation abstraction
```


## Gotchas
- Over-applying delegation when a simpler solution (direct call, if/else) suffices
- Thread safety: delegation implementations often assume single-threaded access
- Testing complexity: mock/stub setup for delegation abstractions can be verbose
