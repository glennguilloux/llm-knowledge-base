# Single Table Inheritance

> **Autogenerated from:** `references/java-design-patterns/single-table-inheritance`

## When to Use
- When you need to decouple single table inheritance implementation from client code
- When the single table inheritance logic varies independently from the rest of the system
- When you want to enforce a consistent single table inheritance interface across implementations
- When the single table inheritance behavior needs to be configured or swapped at runtime
- When standardizing single table inheritance handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The single table inheritance pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep single table inheritance logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle single table inheritance errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the single table inheritance abstraction
```


## Gotchas
- Over-applying single table inheritance when a simpler solution (direct call, if/else) suffices
- Thread safety: single table inheritance implementations often assume single-threaded access
- Testing complexity: mock/stub setup for single table inheritance abstractions can be verbose
