# Transaction Script

> **Autogenerated from:** `references/java-design-patterns/transaction-script`

## When to Use
- When you need to decouple transaction script implementation from client code
- When the transaction script logic varies independently from the rest of the system
- When you want to enforce a consistent transaction script interface across implementations
- When the transaction script behavior needs to be configured or swapped at runtime
- When standardizing transaction script handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The transaction script pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep transaction script logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle transaction script errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the transaction script abstraction
```


## Gotchas
- Over-applying transaction script when a simpler solution (direct call, if/else) suffices
- Thread safety: transaction script implementations often assume single-threaded access
- Testing complexity: mock/stub setup for transaction script abstractions can be verbose
