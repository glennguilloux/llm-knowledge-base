# Trampoline

> **Autogenerated from:** `references/java-design-patterns/trampoline`

## When to Use
- When you need to decouple trampoline implementation from client code
- When the trampoline logic varies independently from the rest of the system
- When you want to enforce a consistent trampoline interface across implementations
- When the trampoline behavior needs to be configured or swapped at runtime
- When standardizing trampoline handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The trampoline pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep trampoline logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle trampoline errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the trampoline abstraction
```


## Gotchas
- Over-applying trampoline when a simpler solution (direct call, if/else) suffices
- Thread safety: trampoline implementations often assume single-threaded access
- Testing complexity: mock/stub setup for trampoline abstractions can be verbose
