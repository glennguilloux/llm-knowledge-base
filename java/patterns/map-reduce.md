# Map Reduce

> **Autogenerated from:** `references/java-design-patterns/map-reduce`

## When to Use
- When you need to decouple map reduce implementation from client code
- When the map reduce logic varies independently from the rest of the system
- When you want to enforce a consistent map reduce interface across implementations
- When the map reduce behavior needs to be configured or swapped at runtime
- When standardizing map reduce handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The map reduce pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep map reduce logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle map reduce errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the map reduce abstraction
```


## Gotchas
- Over-applying map reduce when a simpler solution (direct call, if/else) suffices
- Thread safety: map reduce implementations often assume single-threaded access
- Testing complexity: mock/stub setup for map reduce abstractions can be verbose
