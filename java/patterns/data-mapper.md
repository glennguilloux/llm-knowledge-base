# Data Mapper

> **Autogenerated from:** `references/java-design-patterns/data-mapper`

## When to Use
- When you need to decouple data mapper implementation from client code
- When the data mapper logic varies independently from the rest of the system
- When you want to enforce a consistent data mapper interface across implementations
- When the data mapper behavior needs to be configured or swapped at runtime
- When standardizing data mapper handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The data mapper pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep data mapper logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle data mapper errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the data mapper abstraction
```


## Gotchas
- Over-applying data mapper when a simpler solution (direct call, if/else) suffices
- Thread safety: data mapper implementations often assume single-threaded access
- Testing complexity: mock/stub setup for data mapper abstractions can be verbose
