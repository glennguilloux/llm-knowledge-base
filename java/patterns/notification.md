# Notification

> **Autogenerated from:** `references/java-design-patterns/notification`

## When to Use
- When you need to decouple notification implementation from client code
- When the notification logic varies independently from the rest of the system
- When you want to enforce a consistent notification interface across implementations
- When the notification behavior needs to be configured or swapped at runtime
- When standardizing notification handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The notification pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep notification logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle notification errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the notification abstraction
```


## Gotchas
- Over-applying notification when a simpler solution (direct call, if/else) suffices
- Thread safety: notification implementations often assume single-threaded access
- Testing complexity: mock/stub setup for notification abstractions can be verbose
