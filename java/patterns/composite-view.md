# Composite View

> **Autogenerated from:** `references/java-design-patterns/composite-view`

## When to Use
- When you need to decouple composite view implementation from client code
- When the composite view logic varies independently from the rest of the system
- When you want to enforce a consistent composite view interface across implementations
- When the composite view behavior needs to be configured or swapped at runtime
- When standardizing composite view handling across a team or codebase

## Common Mistakes

```java
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The composite view pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep composite view logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle composite view errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the composite view abstraction
```


## Gotchas
- Over-applying composite view when a simpler solution (direct call, if/else) suffices
- Thread safety: composite view implementations often assume single-threaded access
- Testing complexity: mock/stub setup for composite view abstractions can be verbose
