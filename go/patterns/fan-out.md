# Fan Out

> **Autogenerated from:** `references/go-patterns/messaging`

## When to Use
- When you need to decouple fan out implementation from client code
- When the fan out logic varies independently from the rest of the system
- When you want to enforce a consistent fan out interface across implementations
- When the fan out behavior needs to be configured or swapped at runtime
- When standardizing fan out handling across a team or codebase

## Standard Pattern

```go
// Split a channel into n channels that receive messages in a round-robin fashion.
func Split(ch <-chan int, n int) []<-chan int {
	cs := make([]chan int)
	for i := 0; i < n; i++ {
		cs = append(cs, make(chan int))
	}

	// Distributes the work in a round robin fashion among the stated number
	// of channels until the main channel has been closed. In that case, close
	// all channels and return.
	distributeToChannels := func(ch <-chan int, cs []chan<- int) {
		// Close every channel when the execution ends.
		defer func(cs []chan<- int) {
			for _, c := range cs {
				close(c)
			}
		}(cs)

		for {
			for _, c := range cs {
				select {
				case val, ok := <-ch:
					if !ok {
						return
					}

					c <- val
				}
			}
		}
	}

	go distributeToChannels(ch, cs)

	return cs
}

```

## Common Mistakes

```go
# WRONG: Tight coupling to concrete implementations
# Direct instantiation/usage of specific classes without abstraction layer

# CORRECT: Programming to an interface
# Use an abstraction layer that allows swapping implementations

# WRONG: Violating Single Responsibility
# The fan out pattern handling mixed with unrelated business logic

# CORRECT: Separation of concerns
# Keep fan out logic in dedicated, focused components

# WRONG: Inconsistent error handling
# Different callers handle fan out errors differently

# CORRECT: Centralized error handling
# Use a uniform error handling strategy through the fan out abstraction
```


## Gotchas
- Over-applying fan out when a simpler solution (direct call, if/else) suffices
- Thread safety: fan out implementations often assume single-threaded access
- Testing complexity: mock/stub setup for fan out abstractions can be verbose
