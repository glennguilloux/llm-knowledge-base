# Factory

> **Autogenerated from:** `references/go-patterns/creational`

## When to Use
- When you need to decouple factory implementation from client code
- When the factory logic varies independently from the rest of the system
- When you want to enforce a consistent factory interface across implementations
- When the factory behavior needs to be configured or swapped at runtime
- When standardizing factory handling across a team or codebase

## Standard Pattern

```go
package data

import "io"

type Store interface {
    Open(string) (io.ReadWriteCloser, error)
}


package data

type StorageType int

const (
    DiskStorage StorageType = 1 << iota
    TempStorage
    MemoryStorage
)

func NewStore(t StorageType) Store {
    switch t {
    case MemoryStorage:
        return newMemoryStorage( /*...*/ )
    case DiskStorage:
        return newDiskStorage( /*...*/ )
    default:
        return newTempStorage( /*...*/ )
    }
}


s, _ := data.NewStore(data.MemoryStorage)
f, _ := s.Open("file")

n, _ := f.Write([]byte("data"))
defer f.Close()

```

## Common Mistakes

```go
# WRONG: Tight coupling to concrete classes
Using `new` keyword directly everywhere instead of factory

# CORRECT: Fix
Using a factory method to decouple creation from usage
```

```go
# WRONG: Violating Open/Closed Principle
Modifying factory every time a new type is added

# CORRECT: Fix
Using registration or reflection-based factory that's extensible
```

```go
# WRONG: Complex conditional logic
Long if-else chain to determine which class to instantiate

# CORRECT: Fix
Using a map/dictionary of type -> class for lookup
```


## Gotchas
- Factory methods can obscure the class hierarchy — readers see a method call, not a constructor
- Static factory methods can't be mocked easily; consider instance-based factories for testability
- Abstract Factory and Factory Method solve different problems — don't conflate granularity
